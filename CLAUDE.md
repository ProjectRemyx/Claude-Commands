# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A Salesforce Marketing Cloud (SFMC) HTML email boilerplate for the **AAA Mountain West Group (MWG)** business unit (also covers **A3 Smart Home**). The files here are not built or compiled locally — they are deployed by hand into SFMC Content Builder under `AAA MWG Business Unit > Content Builder > PreVersionControl > BoilerplateV2`. There is no build tool, linter, test runner, package manager, or dev server. "Testing" means uploading to SFMC and previewing with Litmus / Email on Acid / SFMC's preview.

When making changes, your job is almost always to edit HTML / AMPscript that will be copy-pasted (or synced) into SFMC Content Builder. Do **not** introduce JS frameworks, build pipelines, or `package.json`-style tooling.

## High-level architecture

An email is **composed at SFMC send time** from many Content Blocks via AMPscript's `CONTENTBLOCKBYKEY`. The top-level "HTML Email Block" is thin — it just sets two folder IDs and stitches blocks together:

```
SET @BoilerplateFolderID = '399733'   <-- the GlobalModules folder (shared, do not rename)
SET @ProjectFolderID    = '403609'    <-- the per-project folder (changes per email)
CONTENTBLOCKBYKEY(CONCAT(@ProjectFolderID, '_ProjectAmpscript'))   <-- project config + variables
CONTENTBLOCKBYKEY(CONCAT(@BoilerplateFolderID, '_SharedTop01_021825'))
CONTENTBLOCKBYKEY(CONCAT(@BoilerplateFolderID, '_SharedCSS_102425'))
CONTENTBLOCKBYKEY(CONCAT(@BoilerplateFolderID, '_SharedTop02_021825'))
CONTENTBLOCKBYKEY(CONCAT(@BoilerplateFolderID, '_SharedIMAnlytcs_040726'))
CONTENTBLOCKBYKEY(CONCAT(@BoilerplateFolderID, '_SharedTop03_031726'))   <-- LOB header
CONTENTBLOCKBYKEY(CONCAT(@ProjectFolderID,    '_ProjectMiddle01'))       <-- the actual email body
CONTENTBLOCKBYKEY(CONCAT(@BoilerplateFolderID, '_SharedBtm01_031726'))   <-- LOB footer
CONTENTBLOCKBYKEY(CONCAT(@ProjectFolderID,    '_ProjectLegal'))
CONTENTBLOCKBYKEY(CONCAT(@BoilerplateFolderID, '_SharedBtm02_031425'))
```

The three layers:

1. **`GlobalModules/`** — shared, reused across every project. Filenames prefixed `399733_` (the boilerplate folder ID) and suffixed with a `_MMDDYY` date. **Treat date suffixes as part of the identity** — newer dated versions exist alongside older ones (e.g. `SharedBtm01_011526.htm` and `SharedBtm01_031726.htm` coexist). To "update" a shared module you typically create a new dated copy rather than overwriting in place, then update references in HTML Email Blocks to point at the new date. Top/Btm modules cover the `<head>`, fonts, CSS, header, LOB header, LOB footer, blue footer, tracking pixels, and unsubscribe rendering.
2. **`EMC_SAMPLE_MMDDYY/`** — the canonical per-project scaffold. Copy this whole folder to start a new email. It contains:
   - `EMC_SAMPLE_MMDDYY.html` — the HTML Email Block (the stitching file shown above).
   - `ProjectAmpscript.amp` — **the main control panel**. Sets `@BusinessUnit`, `@LOBHeader`, `@LOBFooter`, `@FooterLogo`, `@IncludeMobileAppIcons`, `@LOBunsubscribe`, `@MessageType` (Marketing|Transactional), `@EmailType` (Campaign|Journey|Triggered), `@SubjectLine`, `@PreviewText`, first-name personalization, and the data-spec mapping branch. Every comment block enumerates the valid string values — read them before changing anything.
   - `ProjectMiddle01.htm` — project-specific body content (the only file most projects need to author from scratch).
   - `ProjectCSS.htm` — *optional* override of `SharedCSS_102425`. Only swap in if you need project-specific classes; if used, change the `CONTENTBLOCKBYKEY` to point at `@ProjectFolderID` instead of `@BoilerplateFolderID`.
   - `ProjectLegal.htm` — project-specific legal/disclaimer copy. The scaffold ships **every** legal variant as an example; a real project must be pruned down to what it uses (see the hard constraint below).
   - `EMC_SAMPLE_MMDDYY_NoPTSpacers_ViaHeatmaps_EngageDeployment_FilePassOffTo3rdPartyVendor_only.html` — a flattened, **standalone** variant for Via heatmaps, Engage deployments, or third-party vendor handoffs. Engage cannot resolve robust AMPscript, so this file inlines the CSS, simplifies first-name personalization, and the file header lists the pre-deploy edits required (replace `@SubjectLine`, remove AMPscript wrapper, neutralize IM tracking pixels, etc.). Do not delete those comments.
3. **`BoilerplateV2_ExampleModules/`** — copy-paste reference snippets (buttons, list styles, color swatches, accessible image bullets, web fonts, tables, etc.). Use these as the source of truth when building blocks inside `ProjectMiddle01.htm`. One file here is not a snippet library but a **whole finished email**: `VIA_Highlights_072626_Snapshot.html` is the reference build for the recurring Via Highlights newsletter — a standalone file with the navy Via header, six body modules, and the Via footer all inline. It is the base file for a Via Highlights project (see the `/new-project` Via fork), and like everything else in this folder it is read-only reference.

### Data flow for Campaigns (AAA MWG)

When `@EmailType = 'Campaign'` AND `@BusinessUnit = 'AAA MWG'`, `ProjectAmpscript` pulls in `399733_CmpgnDataSpecVars_010725.amp` which maps a fixed Data Extension layout (the "AAA MWG Email Campaign Data Spec", DE template `AAA_Data_Spec_010725`) into `@SegmentName`, `@FirstName`, `@State`, line-of-business quote fields, etc. Journeys/Triggered sends and A3 Smart Home campaigns hard-code these values directly instead. Do not invent new data field names — extend `CmpgnDataSpecVars` only when the Data Spec itself changes.

### Subject line + IM analytics indirection

`@SubjectLine` is set inside `ProjectAmpscript`, then `399733_SubjectLineController_031025.amp` decorates it with the test prefix using `@ReviewRound` (`DEV`, `R1`, `R2`, ...) and `@ABVersion`. The Subject field in the SFMC HTML Email record must also be populated — `@SubjectLine` is referenced in the rendered HTML in two places (page `<title>` and `aria-label`). `SharedIMAnlytcs` injects Inbox Monster tracking pixels keyed on `@SegmentName` / `@SegmentGeneral` / `@MessageType`.

## Hard constraints (these have bitten people before)

- **CSS weight**: post-send header CSS must stay under **15 kB** or Gmail mobile renders the desktop layout; total post-send code must stay under **102 kB** or Gmail truncates the email. No single CSS line should exceed 998 characters. `ProjectCSS.htm` calls this out at the top — when adding utility classes, prune unused ones.
- **`line-height` is always 1.5 × `font-size`** — 12/18, 14/21, 16/24, 20/30, 24/36, 28/42, 32/48, 36/54, 44/66. This holds for the inline desktop value *and* for the mobile `font-size-*` utility class (each one already ships the matching 1.5× line-height, so never pair a class with a conflicting inline `line-height`). Only two exceptions exist: `<sup>` / `<sub>` use `line-height:0`, and the large display classes `font-size-57` (1.33×), `font-size-64` (1.0×), `font-size-52-special` (1.19×), `font-size-80-special` (1.12×) have deliberately tight leading — don't "fix" those, and don't imitate them at body/heading sizes. **Via Highlights is a third exception, and it is scoped to that one send**: its approved scale ships 34/44 (1.29×), 18/26 (1.44×), and 16/26 (1.63×), with mobile larger than desktop on article headings and eyebrows. Preserve those values verbatim inside a Via Highlights file; never carry them into any other project.
- **First-name personalization lives entirely in `ProjectAmpscript.amp`** — the whole sentence, including any inline HTML, goes in the `@FirstNameIntro*` variable's value; `ProjectMiddle01.htm` only ever outputs `%%=v(@FirstNameIntro)=%%`. Never split a sentence across the boundary (a body ending up with a dangling `…=%%id you know…` fragment means the logic was put in the wrong file). To bold just the name, put the `<span style="font-weight:700">…</span>` *inside* the AMPscript value around `@FirstName` only — the same way `@FirstNameIntro3` already embeds a `<br>`. Write the fallback branch as its own complete, correctly-capitalized sentence rather than trying to splice a leading letter.
- **`ProjectLegal.htm` must be pruned per project.** The scaffold's version is a menu of examples. A real project keeps only: the opening Gmail-iOS comment, the `@IncludeFooterNavCol` table conditional, `<tr>`/`<td>`, the two `gmail-blend-*` divs, the **AAA MWG required-legal** block (`IF @BusinessUnit == 'AAA MWG'` → `IF @RequiredLegal == 'AAA MWG BU Default'` → `FtrRequired01_031425`), the project's own legal paragraphs positioned *below* that block, and — mandatory, always last — the `/* This p must remain at the bottom of this file and must remain open. Do not close. */` comment plus the `<p class="white" style="margin:0 0 42px 0; …">` after it. **That final `<p>` stays unclosed and the file has no closing `</div>`/`</td>`/`</tr>`/`</table>`** — `SharedBtm02` closes all of them. Delete the Lorem numbered footnotes; copy them back from the scaffold only when body copy actually adds a `<sup>`. Two blocks are conditional and worth confirming before deletion: the `@SHSSBSLicenseLegal` → `FtrSHSLicForAAAMWG_011526` block (needed only for **A3 Smart Home** / SHS-SBS security) and the Bread "This message may be considered an advertisement…" paragraph with the `REDIRECTTO(@UnsubscribeURL)` link (needed only for **credit card** emails — it is additional to, not a replacement for, the blue footer's own unsubscribe link).
- **First-name length gate**: `@FirstName` is rejected if `LENGTH < 2`, `LENGTH > 15`, empty, or trim-empty. Personalization variables `@FirstNameSubjectLine` / `@FirstNameIntro*` always fall back to non-personalized copy — preserve this branch when editing.
- **Subject line / Preview text content**: no straight quotes (`'` `"`), no HTML, no `&entities;` in `@SubjectLine`. Replacements: `'` `"` `"` `¹` `²` `³` `™`. Emojis are OK. `@PreviewText` allows entities and emojis but still no straight quotes/HTML. The SFMC **Preheader field** must remain blank — preview text is set in AMPscript.
- **Don't put URLs inside AMPscript variable values** (except `@UnsubscribeURL`) — the variable name leaks into tracking reports instead of the URL. For dynamic URLs, wrap an AMPscript conditional around the entire `<a>` tag in `ProjectMiddle01.htm`.
- **Don't use link aliases for tracking** — Tableau can't display them.
- **Never HTML-escape a URL.** `href` / `src` values are pasted verbatim from the intake, with a literal `&` joining every query param — `&amp;utm_medium=…` is wrong. Entities belong in visible copy, never in an attribute value. (Grep a finished project for `amp;`: any hit inside an `href` is this bug.)
- **`@BusinessUnit` must be exactly `'AAA MWG'` or `'A3 Smart Home'`** — any other value triggers `RAISEERROR` and the email fails to deploy for that record (the rest of the send continues).
- **Gmail iOS dark mode overrides**: any inline `background-color` on a row that needs to stay its set color (especially blues, blacks, slate) requires a paired `background-image:linear-gradient(<color>,<color>)`. Any white text needs the `gmail-blend-screen` / `gmail-blend-difference` wrappers. Both patterns are everywhere in `ProjectMiddle01.htm` and the example modules — copy them; don't simplify them away.
- **Outlook (MSO) conditionals**: button spacing relies on `<!--[if mso]><em style="letter-spacing:25px; mso-font-width:-100%; mso-text-raise:30pt;">&nbsp;</em><![endif]-->` padding hacks around button labels. Mobile vs. desktop image swaps use paired `<!--[if !mso]><!-->` / `<!--<![endif]-->` and `class="mobile-hidden"` blocks. Don't collapse these.

## Table markup rules (strict)

Email clients still require table-based layout for reliable rendering. Follow these rules without exception when authoring or editing markup:

- **Every `<table>` must have all of these attributes**: `align="..."`, `border="0"`, `cellpadding="0"`, `cellspacing="0"`, and `role="presentation"`. The `role="presentation"` is critical for accessibility — it tells screen readers the table is layout, not tabular data.
- **Width belongs in the `style` attribute**, not as an HTML `width="..."` attribute on the table. Example: `style="width:640px"` (or `style="width:580px; background-color:#ffffff;"`). The HTML `width` attribute is reserved for `<img>` and `<td>` cells where it actually helps Outlook.
- **Nesting and width classes**: outer (top-level wrapper) tables do **not** need a width utility class. Inner / nested tables should carry the appropriate responsive class — most commonly `class="w-100"` (full width on mobile) or `class="w-90"` (90% on mobile) on the second table in the nest. Match the surrounding nesting pattern you see in `ProjectMiddle01.htm` and `BoilerplateV2_ExampleModules/`.
- **Avoid `<div>` for layout** — it breaks accessibility and Outlook rendering. Use `<table>` / `<tr>` / `<td>` for structure. `<div>` is acceptable only for the documented Gmail iOS dark-mode wrappers (`gmail-blend-screen` / `gmail-blend-difference`), the hidden preview-text div, and the mobile-only image swap wrappers. Some newer modules contain layout `<div>`s that were left in for speed of delivery — do not treat those as the pattern to follow; prefer the table-based equivalents from the example modules.
- For tabular data (where the table really is data, not layout), use `Modules_AccessibleTablesForTabularData.html` in `BoilerplateV2_ExampleModules/` as the reference. Do **not** put `role="presentation"` on a real data table.

## Editing conventions

- The valid values for `@LOBHeader`, `@LOBFooter`, `@FooterLogo`, `@IncludeFooterNavCol`, `@LOBunsubscribe`, `@CustomMemberBusName`, etc. are **enumerated inline as comments** in `ProjectAmpscript.amp`. Stay within those lists; if a new option is needed, the corresponding GlobalModule (`SharedTop03_*`, `SharedBtm01_*`, `LOBunsubscribe_*`) must also support it.
- File naming: GlobalModules use `399733_<Name>_<MMDDYY>.<ext>`. Per-project files use `<ProjectCode>_<MMDDYY>` (e.g. `EMC_SAMPLE_MMDDYY`). The `EMC_` prefix indicates "Email Marketing Campaign"; preserve the date suffix when copying — it becomes the version identifier in SFMC.
- AMPscript comments use the `%%[/* … */]%%` form at the top-level (where SFMC needs the `%%[…]%%` evaluation context) and bare `/* … */` inside an already-open `%%[ … ]%%` block. Match the surrounding style — do not switch forms.
- The doc that explains Header / LOB Footer / Footer use cases lives in Google Sheets: `https://docs.google.com/spreadsheets/d/1uan7zwkVDPKc7qUBA_rbhPcaK_mDeXXruwB4zDvvPFE` (linked at the top of `ProjectAmpscript.amp`).

## Project-bootstrap automation (slash commands)

Custom slash commands live in `.claude/commands/`. Use these to skip the manual setup steps and jump straight into authoring `ProjectMiddle01.htm`. They are versioned separately in the **Claude-Commands** repo (`https://github.com/ProjectRemyx/Claude-Commands`) along with the helper scripts below — that repo is the source of truth, so pull from it rather than editing these in isolation.

- **`/new-project [intake.doc]`** — parses the Email Intake Form, which arrives as a **Jira ticket export in Microsoft Word `.doc` format** (e.g. `DC-1185.doc`). The user supplies the path; the command never auto-discovers an intake. Shows the proposed AMPscript variable mappings for confirmation, asks which HTML Email Block variant to use (Standard vs. NoPTSpacers/Engage/Vendor), copies `EMC_SAMPLE_MMDDYY/` into `E:\Lumenalta\AAA SFMC Files\<YEAR>\<campaign_name>\`, strips the scaffold's reference material out of the new `assets/`, renames the scaffold files, and pre-fills `ProjectAmpscript.amp` + `ProjectLegal.htm`. `<YEAR>` is parsed from the trailing `_MMDDYY` in the campaign name (NOT today's date). A single ticket is usually one email of a multi-email journey — the siblings are separate tickets, so the command is run once per ticket.
  - **A/B test fork**: when the ticket says `A/B Test: Yes`, the project stays **one folder with one `@ProjectFolderID`** but gets **two HTML Email Blocks** — named after `Campaign Name A` and `Campaign Name B` — each carrying a new `SET @email_version = 'A'` / `'B'` line directly under `SET @ProjectFolderID`. Because that line precedes every `CONTENTBLOCKBYKEY` call, the shared `ProjectAmpscript` / `ProjectMiddle01` / `ProjectLegal` blocks can branch on `@email_version` to toggle whatever the test changes; `@ABVersion` is wired to it (`SET @ABVersion = @email_version`) so each variant's test subject line carries its own letter.
  - **Via Highlights fork**: when the user picks the **Standalone** variant, the command asks whether it's a Via Highlights send (it always asks — a `VIA_` campaign name only pre-selects the answer, because Via also runs non-Highlights single-file sends). On yes it takes over the `/generate-projectmiddle01` job in the same run, because the Highlights layout is fixed and only images, copy, URLs, and the footer's photo credits change per issue. The base file becomes `BoilerplateV2_ExampleModules/VIA_Highlights_072626_Snapshot.html` (**not** the scaffold's standalone, which lacks the inline Via navy header/footer and the Via-only mobile classes `btn-mobile`, `hed-mobile`, `buttom-mobile-padding-small`, `buttom-btn-pad`, `padding-left-0`), and `ProjectAmpscript.amp` / `ProjectMiddle01.htm` / `ProjectCSS.htm` / `ProjectLegal.htm` are deleted — the Via build is one self-contained file with its AMPscript, CSS, and legal inline. Two Via-specific traps the command handles: the snapshot omits `SET @MessageType`, so the Inbox Monster block silently tags the send **Transactional** unless `'Marketing'` is added; and Via's approved type scale deliberately breaks the 1.5× line-height rule (34/44, 18/26, 16/26) with mobile larger than desktop on article headings and eyebrows — preserve those, don't "fix" them. A section that matches none of the six Via modules is escalated to the developer with the same build-by-hand / FPO-placeholder / something-else options `/generate-projectmiddle01` uses.
- **`/generate-projectmiddle01 [project-folder]`** — **not used for Via Highlights** (see the fork above). User attaches a PDF export (desktop + mobile) or screenshots of the Figma creative. Measures background bands, rounded cards, image bboxes and the full desktop↔mobile type scale via `parse_creative_pdf.py`, renders high-zoom crops to read font weight and copy, pulls the real tracking URLs from the ticket's Campaign URLs table, proposes a top-to-bottom sequence of modules from `Modules_V3_Styles.html` (and the other `BoilerplateV2_ExampleModules/` files) with per-variant rationale, waits for approval, then stitches them in and applies the measured spec — copy, font sizes, weights, background colors, alt text, and `href`s.
- **`/edit-data-extension [project-folder]`** — lists the 22 tabs in the project's `assets/<project>.xls`, asks (with recommendations based on LOB / seed-list from the intake) which to keep, prunes the rest via Excel COM, then dedupes the duplicate `SAMPLE_EMC_VALUE<digit>_MMDDYY` sample sets and sets Segment Name / Segment General to the campaign name. Requires Excel installed (uses `pywin32`).

There is no longer a separate `/add-module` command — `/generate-projectmiddle01` performs the same snippet extraction and table-markup validation inline, so module insertion is part of that flow.

Helper scripts in `.claude/scripts/`:

- `parse_intake.py` — reads the intake `.doc` (Jira ticket export) via Word COM and emits structured JSON used by `/new-project` and `/generate-projectmiddle01`: `raw`, `derived`, `ampscript_proposed`, `extras`, and `campaign_urls`. `derived` carries `is_ab_test` (from the ticket's `A/B Test` field) and `campaign_name_a` / `campaign_name_b`, which drive the A/B two-file fork above — `campaign_name_b` falls back to `<A>_B` when the ticket leaves the field blank, so the command confirms it with the user. That last one parses the ticket's **Campaign URLs** table into `{placement, section, type, cell_instructions, url}` rows — `section` comes from a `(section N)` prefix and matches the section order in the creative, so a URL maps straight to a module. Dependencies: `pywin32`.
- `de_tabs.py` — `list` (read-only via `xlrd`), `keep <tabs...>`, and `finalize <campaign-name>` (both Excel COM via `pywin32`) for the data-extension `.xls`. `finalize` deletes the duplicate `SAMPLE_EMC_VALUE<digit>_MMDDYY` rows and rewrites Segment Name / Segment General on every remaining tab. Saves back as Excel 97-2003 format 56.
- `parse_creative_pdf.py` — measures a Figma PDF export of a creative for `/generate-projectmiddle01`: background bands with palette names, rounded cards, image bboxes, and every text line's size / line-height / color / alignment. Pass `--mobile <pdf>` for a second export to get the desktop↔mobile type scale paired with the right `font-size-*` class. Figma exports at 640px (desktop) / 320px (mobile), so PDF points map 1:1 to CSS px. Dependencies: `pymupdf`.

Python toolchain assumed (already installed at the time these were written): Python 3.12 via `py`, `openpyxl`, `xlrd` 2.0.1, `xlwt`, `pywin32`, `pymupdf`.

## Things this repo does NOT have

No `npm`, no `pip`, no MJML, no Foundation for Emails, no Jinja/Liquid templating, no preview server, no automated tests. The only "scripting language" present is **AMPscript**, which only runs server-side inside SFMC. Don't try to execute `.amp` files locally.
